Where in France should you run your AI?

A pipeline that runs every hour and ranks French regions by how harmful it is to run AI workloads there, using both carbon and water.

AirflowSparkDockerParquetElasticsearchKibana
Read the case study

The problem. Data centres use electricity, and they also use a lot of water for cooling. France's grid is clean everywhere, so electricity data alone cannot tell two regions apart. Water stress changes by region and by season.

The data. Two live APIs. Electricity Maps gives the carbon intensity of the French grid every hour (typically 14–19 gCO₂/kWh, against 400+ in Germany or Poland). Hub'eau, the official French hydrology platform, gives river flow in litres per second at 5 gauging stations, one per region, which I used as a proxy for water availability.

The architecture. A 7-task Airflow DAG, run in Docker, moves data through four datalake layers: raw, formatted, usage and exposition. Spark turns the raw JSON into Parquet, computes the scores, and loads them into Elasticsearch for Kibana dashboards.

The Sustainability Guardrail. A score that combines an energy stress (carbon intensity against France's historical average) with a water stress (river flow against thresholds from research on ecological minimum flows).

Result. The Garonne near Bordeaux flows at over 20,000 L/s, about 17 times more than the rivers monitored near Paris or Lyon, which flips the regional ranking. Nouvelle-Aquitaine and Occitanie come out as better places for water-cooled data centres than the Paris basin. Because the pipeline runs hourly, the ranking can change, for example in a dry summer.

Bilingual document Q&A chatbot

A French and English chatbot that answers from your PDFs and shows where each answer came from.

PythonFlaskChromaDBPhi-3Ollama
Read the case study

The problem. Chatbots can sound sure and still be wrong. For documents, people need to check the answer against the page.

What I built. Python and Flask app using Sentence-Transformers and ChromaDB to find passages, with a local Phi-3 model through Ollama writing the answer. Each answer returns the source file and page. Users can upload new PDFs without rebuilding the app.

Result. Answers take about 3 seconds. There is a live demo on Hugging Face Spaces, and the Flask API runs in Docker.

AeroGuard: poaching detection

A YOLO model on a Raspberry Pi that spots animals, fire, vehicles and people and sends an SMS.

YOLOPyTorchRaspberry PiTwilio
Read the case study

The problem. Remote areas need fast warnings, and there is no powerful server nearby to run detection.

What I built. A YOLO/PyTorch detector running on a Raspberry Pi 4, connected to Twilio so a detection triggers a text message.

Result. 92% mAP, with SMS alerts sent in under 2 seconds.

Resume screening for HR

A BERT and spaCy model that scores and ranks job candidates, built with the HR team at Param Group.

BERTspaCyRanking
Read the case study

The problem. HR had many resumes to read, and a score is only useful if people know how it was made.

What I built. A BERT/spaCy model that scores and ranks candidates from resume data. I then walked HR through how the scores are produced and where they should not be trusted.

Result. HR received a ranking they could understand and question.
